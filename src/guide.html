۱۶ آبان ۱۴۰۵ | نسخه ۱.۲ راهنما

راهنمای اتصال شریک‌ها به فان‌لندز

این سند برای تیم فنی هر شریکیه که می‌خواد بازی‌های فان‌لندز رو داخل سرویس خودش نشون بده. تیم‌های داخلی خودمون هم که روی ماژول شریک یا کلاینت بازی کار می‌کنن همین رو مبنا می‌ذارن. مبنای این متن قرارداد یکپارچه‌سازی فان‌لندز نسخه ۲.۰ هست. اینجا همون قرارداد رو به زبان اجرایی نوشتیم و هر جا چیزی باز مونده بود، تصمیم خودمون رو گذاشتیم. توی بخش ۱۰ هم نمونه کد NestJS برای همه کارهای سمت شریک اومده. اگه جایی این متن با قرارداد نخونه، قرارداد ملاکه و لطفا به ما خبر بدید.

اصل اعتماد

هر طرف با کلید خصوصی خودش امضا می‌کنه و کلید عمومیش رو روی یک نشانی JWKS منتشر می‌کنه. هیچ کلید خصوصی یا سکرت مشترکی بین ما و شریک جابه‌جا نمیشه.

هر پوسته یک شریک

هر پوسته یک شریک جداست با شناسه، کلید، داده و پنل خودش. هیچ شریکی داده شریک دیگه رو نمی‌بینه.

دو محیط جدا

sandbox و production کاملا از هم جدا هستن: کلید، issuer، audience، client_id، داده، وب‌هوک و پنل. توکن یک محیط توی محیط دیگه رد میشه و یک sub یکسان توی این دو محیط دو بازیکن جدا در فان‌لندزه.

نمونه‌ها

دامنه‌هایی مثل api.sandbox.funlands.example، play.sandbox.funlands.example و partner.example نشانی واقعی هیچ سرویسی نیستن و همه کلیدها، client_idها، scopeها و شناسه‌های این متن هم نمونه‌ان. نشانی‌ها، کلیدها، client_id و scopeهای واقعی هر محیط فقط از برگ شریک میان.

وضعیت: مسیرهای این راهنما، یعنی JWKS فان‌لندز، ورود وب، bootstrap و refresh، خروج، توکن گزارش، گزارش‌ها و وب‌هوک، الان در حال پیاده‌سازی هستن و هنوز روی sandbox باز نشدن. وقتی sandbox آماده شد نشانی‌های واقعی رو توی برگ شریک می‌فرستیم. ورود اپ بومی، حذف حساب و API رویدادهای فنی بازی هنوز طراحی نهایی ندارن و توی بخش ۱۲ اومدن.
تغییرات نسخه ۱.۲ (۱۶ آبان ۱۴۰۵): فضای شریک حالا از access token بازیکن خونده میشه. صفحه بازی بعد از bootstrap فقط Authorization: Bearer (و توی WebSocket فقط auth.token) می‌فرسته و دیگه x-partner-api-key نمی‌خواد، پس بازیکن‌های شریک‌های server_to_server هم بدون هیچ سکرتی از مرورگر بازی می‌کنن (بخش ۴.۷). رفتار توکن‌ها بعد از غیرفعال شدن شریک، issuer فان‌لندز روی SETها، مقدار result و تعریف شاخص‌های گزارش هم دقیق‌تر شدن. نسخه ۱.۱ فرم launch و bootstrap رو به Origin بازی فان‌لندز (FUNLANDS_GAME_ORIGIN) برده بود و مشخص کرده بود که funlands:relaunch_requested رو خود صفحه بازی می‌فرسته (بخش ۴.۹).

۱. اتصال در یک نگاه

اتصال شریک به فان‌لندز روی این چند قاعده ساخته شده:

  • هر کار توکن خودش رو داره: توکن launch با عمر حداکثر ۱۲۰ ثانیه، access بازی ۱۵ دقیقه، refresh چرخشی با سقف ۱۲ ساعت، و یک توکن جدا برای گزارش. هیچ توکن بلندمدتی برای کاربر صادر نمیشه.
  • هر طرف فقط نشانی JWKS خودش رو ثبت می‌کنه. نه فایل کلید رد و بدل میشه نه سکرت مشترک، و چرخش و ابطال کلید روال مشخص داره.
  • ورود وب با یک فرم POST داخل iframe انجام میشه و یک verifier کد bootstrap رو به همون پنجره گره می‌زنه. هیچ توکن یا کدی توی URL نمیره.
  • رویدادها با وب‌هوک امضاشده در قالب SET می‌رسن، شناسه event_id ثابته، تا ۷۲ ساعت دوباره فرستاده میشن و یک API هم برای گرفتن رویدادهای جامونده هست.
  • خروج کاربر با یک پیام امضاشده از سرور شریک انجام میشه و اثرش فوریه.
  • خطاها کد پایدار دارن و برای هر کد گفتیم شریک چی کار کنه.

نمونه پیاده‌سازی سمت شریک با NestJS توی بخش ۱۰ هست.

۲.۳ جدایی sandbox و production

  • برای هر محیط یک رکورد جدا داریم با issuer، JWKS، الگوریتم، audienceها، Originها، وب‌هوک، client_id، داده و پنل خودش.
  • کلید امضای sandbox و production هیچ‌وقت یکی نیست. توکن sandbox روی production با AUDIENCE_MISMATCH رد میشه و برعکس.
  • توی sandbox فقط داده غیرواقعی بفرستید. شناسه کاربر واقعی رو برای تست استفاده نکنید.
  • بازیکن‌ها برای هر محیط جدا ساخته میشن: اگه یک sub هم توی sandbox و هم توی production وارد بشه، دو حساب جدا در فان‌لندز داره و داده بازی، نشست‌ها و گزارش‌هاش هیچ‌وقت قاطی نمیشن.

۲.۴ مسیر رسیدن به production

  1. شریک برگ بخش ۲.۱ رو برای sandbox پر می‌کنه و از یک کانال اداری احرازشده برامون می‌فرسته. نشانی JWKS رو فقط از همین کانال ثبت می‌کنیم، نه از داخل توکن.
  2. ما رکورد sandbox رو می‌سازیم، JWKS شما رو یک بار می‌خونیم و چک می‌کنیم کلیدها درست باشن، الگوریتم مجاز باشه و هر کلید kid داشته باشه. بعد مقدارهای بخش ۲.۲ رو می‌فرستیم.
  3. شریک آزمون انطباق رو روی sandbox اجرا می‌کنه تا همه موارد پاس بشن، و بعد ترافیک آزمایشی با داده غیرواقعی می‌فرسته.
  4. مالک امنیت دو طرف تست‌های منفی توکن و تمرین چرخش کلید رو امضا می‌کنن. برگ داده، فهرست رویدادها، تعریف شاخص‌ها و روال حادثه هم با مالک مشخص تایید میشن.
  5. رکورد production با کلیدهای جدید و مقدارهای جدا ثبت میشه و ترافیک واقعی اول به‌صورت محدود باز میشه.

۳. کلیدها

۳.۱ قاعده‌های اصلی

  • هر طرف با کلید خصوصی خودش امضا می‌کنه. کلید خصوصی توی KMS یا HSM همون سازمان می‌مونه و به هیچ‌کس داده نمیشه، نه از طریق API، نه با ایمیل، نه «دستی» برای راه افتادن سریع. ما هم هیچ‌وقت چنین چیزی نمی‌خوایم. اگه کسی از طرف فان‌لندز کلید خصوصی خواست، این خودش یک حادثه امنیتیه.
  • سکرت مشترک هم نداریم. الگوریتم none و کل خانواده HS256/HS384/HS512 رد میشن.
  • کلید عمومی رو فقط از نشانی JWKS ثبت‌شده همون issuer و همون محیط می‌خونیم. هدرهای jku، x5u، jwk و x5c منبع کلید نیستن و crit هم قبول نمیشه. توکنی که هر کدوم از این هدرها رو داشته باشه با TOKEN_TYPE_INVALID رد میشه.
  • الگوریتم رو از برگ شریک برمی‌داریم، نه از هدر توکن. برای هر محیط یک الگوریتم ثابت ثبت میشه. پیشنهاد ما ES256 (منحنی P-256) هست. RS256، PS256 و EdDSA هم پشتیبانی میشن، و برای RSA کلید باید دست‌کم ۲۰۴۸ بیت باشه. عوض کردن الگوریتم چرخش کلید حساب نمیشه، تغییر سیاسته و تست دوباره می‌خواد.
  • اختلاف ساعت مجاز برای همه توکن‌ها ۳۰ ثانیه‌ست. ساعت سرورها رو با NTP هماهنگ نگه دارید.

۳.۲ JWKS شریک

نشانی JWKS باید HTTPS باشه، بدون ریدایرکت جواب بده و فقط کلید عمومی داشته باشه. وجود d، p، q یا هر پارامتر خصوصی دیگه خطای امنیتیه و اون JWKS رو قبول نمی‌کنیم. هر کلید باید kid، alg و use: "sig" داشته باشه.

GET https://auth.sandbox.partner.example/.well-known/jwks.json

{
  "keys": [{
    "kty": "EC", "crv": "P-256", "use": "sig", "alg": "ES256",
    "kid": "partner-a-sandbox-2026-11",
    "x": "<base64url-public-x>", "y": "<base64url-public-y>"
  }]
}

رفتار ما موقع خوندن JWKS شما:

  • فقط نشانی ثبت‌شده رو می‌خونیم. ریدایرکت رو دنبال نمی‌کنیم و به نشانی‌های داخلی یا خصوصی وصل نمیشیم.
  • timeout سه ثانیه‌ست، پاسخ حداکثر ۶۴ کیلوبایت و حداکثر ۲۰ کلید. JWKS رو ۵ دقیقه کش می‌کنیم.
  • اگه توکنی با kid ناشناخته برسه، یک بار JWKS رو دوباره می‌خونیم (برای هر محیط حداکثر یک بار در هر ۳۰ ثانیه). اگه باز هم کلید نبود، توکن با KEY_NOT_FOUND رد میشه.
  • اگه JWKS در دسترس نباشه، فقط کلیدهایی که قبلا معتبر و کش شده بودن تا حداکثر یک ساعت قبول میشن. کلید ناشناخته یا ابطال‌شده رو به خاطر قطعی هیچ‌وقت قبول نمی‌کنیم.

۳.۳ قاعده‌های kid

  • kid باید رشته غیرخالی باشه و توی issuer و محیط شما یکتا باشه. لازم نیست بین شریک‌ها یکتا باشه، چون ما کلید رو با جفت issuer و kid پیدا می‌کنیم.
  • kid یک کلید قدیمی رو هیچ‌وقت برای کلید جدید استفاده نکنید.
  • پیشنهاد قالب: <نام شریک>-<محیط>-<سال-ماه>، مثلا partner-a-sandbox-2026-11.

۳.۴ چرخش برنامه‌ریزی‌شده کلید شریک

  1. کلید جدید K2 رو با kid تازه توی KMS بسازید. هنوز با K1 امضا کنید.
  2. K1 و K2 رو با هم توی JWKS منتشر کنید.
  3. دست‌کم ۲۴ ساعت صبر کنید. از نظر فنی بیشترین زمان کش ما به‌اضافه یک حاشیه کافیه، ولی ۲۴ ساعت جلوی مشکل کش‌های میانی رو هم می‌گیره.
  4. همه توکن‌ها رو با K2 امضا کنید: launch، logout و client assertion. ما کلید رو با kid انتخاب می‌کنیم و در این مدت هر دو کلید رو قبول می‌کنیم.
  5. K1 رو دست‌کم ۲۴ ساعت بعد از آخرین امضا با اون توی JWKS نگه دارید، بعد حذفش کنید. از نظر فنی بلندترین عمر توکن شما (۱۲۰ ثانیه) به‌اضافه ۳۰ ثانیه اختلاف ساعت و زمان کش کافیه.
  6. پیشنهاد ما اینه که کلیدها رو دست‌کم هر ۱۸۰ روز عوض کنید و هر بار چرخش رو اول روی sandbox تمرین کنید.

۳.۵ چرخش برنامه‌ریزی‌شده کلید فان‌لندز

  1. کلید جدید ما دست‌کم ۲۴ ساعت قبل از اولین استفاده توی JWKS فان‌لندز منتشر میشه. JWKS ما Cache-Control: public, max-age=300 برمی‌گردونه.
  2. بعد SETهای جدید با کلید جدید امضا میشن. رویدادهایی که دوباره فرستاده میشن هم امضای تازه با کلید جدید می‌گیرن ولی event_id قبلی رو نگه می‌دارن.
  3. کلید قدیمی دست‌کم ۲۴ ساعت بعد از آخرین امضا توی JWKS می‌مونه.
  4. سمت شما: کلید ما رو توی کد ثابت نکنید. با kid از JWKS ما انتخاب کنید، کش رو حداکثر ۱۰ دقیقه نگه دارید و برای kid ناشناخته یک بار و با محدودیت نرخ دوباره بخونید.

۳.۶ ابطال اضطراری، وقتی کلید شریک لو رفته

حذف کردن کلید از JWKS به‌تنهایی کافی نیست، چون نسخه کش‌شده تا چند دقیقه هنوز اون کلید رو داره. ابطال واقعی با اعلام مستقیم و denylist انجام میشه.

  1. امضا با K1 رو همون لحظه متوقف کنید و K1 رو توی KMS غیرفعال کنید.
  2. از کانال حادثه‌ای که توی برگ شریک ثبت شده به ما خبر بدید: issuer، محیط، kid لو رفته و بازه زمانی‌ای که کلید در خطر بوده. این پیام نباید با کلید لو رفته امضا یا تایید بشه.
  3. ما جفت issuer و kid رو برای اون محیط فورا توی denylist می‌ذاریم. denylist بر کش اولویت داره، پس هر توکن K1، حتی با exp معتبر، رد میشه.
  4. نشست‌هایی که توی بازه خطر ساخته شدن رو طبق روال حادثه باطل می‌کنیم. اگه دامنه نشت روشن نباشه، ورود جدید اون محیط رو موقتا می‌بندیم.
  5. K2 رو با kid تازه منتشر کنید و K1 رو از JWKS بردارید. با اولین توکن K2 ما JWKS رو دوباره می‌خونیم.
  6. بعد از حادثه یک گزارش کوتاه رد و بدل می‌کنیم. اگه همون کلید برای client assertion گزارش هم استفاده میشده، اون هم باید عوض بشه.

۳.۷ ابطال اضطراری، وقتی کلید فان‌لندز لو رفته

  1. ما امضا با K1 و اگه لازم باشه ارسال وب‌هوک رو متوقف می‌کنیم و K2 رو فعال می‌کنیم.
  2. از کانال حادثه ثبت‌شده به شما خبر می‌دیم، با kid لو رفته و زمان.
  3. شما kid رو فورا توی denylist خودتون بذارید و هر SET که با K1 امضا شده رو رد کنید، حتی اگه تازه باشه.
  4. بعد از رفع مشکل، رویدادهای تحویل‌نشده با امضای تازه و همون event_id دوباره ارسال میشن.

۴. ورود بازی در وب

۴.۱ مراحل در یک نگاه

  1. کاربر توی سرویس شما وارد شده و شما چک کردید که این بازی براش مجازه.
  2. سرور شما یک bootstrap_verifier تصادفی تازه می‌سازه و launch_challenge رو ازش حساب می‌کنه.
  3. سرور شما توکن launch رو با کلید خصوصی امضا می‌کنه. توکن هیچ‌وقت توی مرورگر یا اپ ساخته نمیشه.
  4. صفحه شما یک iframe و یک فرم مخفی داره که launch_token، bootstrap_verifier و game رو با POST به /v1/partner/launch روی Origin بازی فان‌لندز (FUNLANDS_GAME_ORIGIN) داخل همون iframe می‌فرسته.
  5. فان‌لندز درخواست رو چک می‌کنه، بازیکن رو پیدا می‌کنه یا می‌سازه، یک نشست می‌سازه و یک صفحه HTML برمی‌گردونه.
  6. اون صفحه داخل iframe کد bootstrap رو با همون verifier عوض می‌کنه و توکن‌های بازی رو می‌گیره. این قدم و refresh کار خود صفحه بازیه و سرور شما کاری نمی‌کنه.

۴.۳ verifier و ساخت توکن

برای هر ورود یک verifier تازه بسازید و هیچ‌وقت تکرارش نکنید. نمونه کوتاه با Node.js و کتابخونه jose اینه و نسخه کامل NestJS توی بخش ۱۰.۳ هست:

import { randomBytes, createHash, randomUUID } from 'node:crypto';
import { SignJWT } from 'jose';

const verifier  = randomBytes(32).toString('base64url');
const challenge = createHash('sha256').update(verifier, 'ascii').digest('base64url');

const now = Math.floor(Date.now() / 1000);   // one clock read: exp - iat stays exactly 120
const launchToken = await new SignJWT({ sid, game, launch_challenge: challenge })
  .setProtectedHeader({ alg: 'ES256', typ: 'funlands-launch+jwt', kid: ACTIVE_KID })
  .setIssuer(ISSUER)
  .setAudience(LAUNCH_AUDIENCE)
  .setSubject(pairwiseSub)
  .setIssuedAt(now)
  .setExpirationTime(now + 120)
  .setJti(randomUUID())
  .sign(signer);   // production: sign inside KMS or HSM

۴.۵ چیزهایی که ما چک می‌کنیم

  1. حجم درخواست، Content-Type، محدودیت نرخ و Origin.
  2. هدر و iss رو فقط برای پیدا کردن رکورد شریک می‌خونیم. تا امضا تایید نشه به هیچ‌کدوم اعتماد نمی‌کنیم.
  3. typ، الگوریتم، kid، نبودن هدرهای ممنوع و denylist.
  4. امضا با کلید JWKS ثبت‌شده، بعد همه claimها، برابری game با فرم، و برابری SHA-256(bootstrap_verifier) با launch_challenge.
  5. یک‌بارمصرف بودن jti با یک رکورد ماندگار در دیتابیس. ساخت بازیکن، نشست و رویدادهای player.created و session.started همه توی یک تراکنش انجام میشه.

صفحه بازی از همون endpoint تمدید نشست عادی فان‌لندز استفاده می‌کنه. بدنه و پاسخش camelCase هستن و پاسخ موفق داخل پاکت { "state": true, "data": ... } میاد:

Content-Type: application/json

200 OK
{ "state": true,
  "data": { "accessToken": "<funlands-jwt>", "refreshToken": "<rotated-opaque-token>",
            "accessTokenExpiresAt": "2026-11-05T09:45:00.000Z",
            "refreshTokenExpiresAt": "2026-11-05T21:30:00.000Z" } }
  • هر refresh موفق یک access و یک refresh تازه میده و refresh قبلی مصرف میشه.
  • توکن‌ها توی localStorage نگه داشته نمیشن. اگه صفحه reload بشه، ممکنه refresh از دست بره و ورود دوباره لازم بشه.
  • refresh ناشناخته یا منقضی، یا refresh بعد از سقف ۱۲ ساعت، جواب 401 TOKEN_EXPIRED می‌گیره.
  • اگه یک refresh که قبلا چرخیده دوباره استفاده بشه، همه نشست‌های اون بازیکن باطل میشن و جواب 401 TOKEN_REUSE هست. کاربر باید دوباره از طریق شما وارد بشه. پس دو refresh هم‌زمان با یک توکن نفرستید.
  • بعد از خروج back-channel، فان‌لندز نشست رو همون موقع حذف می‌کنه، پس refresh معمولا جواب 401 TOKEN_EXPIRED می‌گیره، همون کدی که access token اون نشست هم از این به بعد می‌گیره. 401 SESSION_REVOKED فقط وقتی میاد که refresh قبل از حذف نشست برسه: مثلا وقتی خروج یا غیرفعال شدن محیط ثبت شده ولی بستن نشست هنوز تموم نشده (خروجی که 503 گرفته و هنوز تکرار نشده).
  • اگه شریک غیرفعال بشه، access token همه بازیکن‌هاش از همون لحظه روی هر درخواستی که کاربر لازم داره و روی handshake جواب 401 TOKEN_EXPIRED می‌گیره. روی مسیرهای عمومی، درخواست بدون کاربر ادامه پیدا می‌کنه. refresh نشستی که هنوز حذف نشده 401 SESSION_REVOKED می‌گیره و همون موقع حذف میشه. نشستی که با launch باز شده با غیرفعال شدن شریک باطل میشه و کمی بعد حذف میشه، و از اون به بعد refreshش TOKEN_EXPIRED می‌گیره. نشستی که بدون launch باز شده (OTP، رمز یا مهمان با کلید همون شریک) تا اولین refresh می‌مونه و همون refresh با SESSION_REVOKED رد میشه. اتصال‌های WebSocket باز هم توی ضربان بعدی، حدود ۲۵ ثانیه، بسته میشن.
  • خود bootstrap هم وقتی 401 SESSION_REVOKED می‌گیره که خروج همون sid زودتر از bootstrap رسیده باشه.
  • صفحه بازی TOKEN_EXPIRED و SESSION_REVOKED رو «نشست تموم شده» حساب می‌کنه، دوباره refresh نمی‌کنه و ورود دوباره می‌خواد (بخش ۴.۹).

بعد از bootstrap، صفحه بازی روی هر درخواست HTTP به APIهای بازی فقط Authorization: Bearer <access_token> رو می‌فرسته و روی هر اتصال WebSocket همین توکن رو با auth.token در handshake میده. هیچ کلید شریکی لازم نیست: access token بازیکن شریک، شریک خودش رو با خودش داره و فان‌لندز فضای شریک رو از توکن تاییدشده می‌خونه. refresh هم هدر شریک نمی‌خواد. برای همین بازیکن‌های شریک‌های server_to_server هم فقط با همین توکن از مرورگر بازی می‌کنن و هیچ سکرتی به مرورگر نمی‌رسه.

  • کلیدهای شریک اختیاری‌ان و فقط برای درخواست‌های بدون توکن به کار میان (OTP، ورود، مهمان و خوندن‌های عمومی)، اونم اگه شریک از این مسیرها استفاده کنه. شریک client_direct برای این کار x-partner-api-key رو می‌فرسته. X-Partner-Public-Key و X-Partner-Secret شریک‌های server_to_server فقط سمت سرور می‌مونن و هیچ‌وقت نباید به مرورگر، اپ یا صفحه بازی برسن.
  • اگه درخواست یا handshakeی که توکن داره کلید شریک هم داشته باشه، اون کلید باید مال همون شریکی باشه که توکن براش صادر شده، وگرنه جواب 403 PARTNER_TOKEN_MISMATCH هست. توکن پلتفرم، یعنی توکنی که مال هیچ شریکی نیست، همراه کلید شریک همین جواب رو می‌گیره.
  • کلید ناشناخته یا چرخیده روی هر درخواستی 401 PARTNER_KEY_INVALID می‌گیره و با refresh درست نمیشه.

۴.۸ تکرار درخواست ورود

  • اگه همون توکن با همون محتوا و همون verifier درست دوباره برسه، مثلا چون شبکه قطع شده، نشست دوم ساخته نمیشه و یک کد bootstrap تازه برای همون نشست برمی‌گرده. این کار حداکثر سه بار و فقط تا قبل از exp ممکنه.
  • اگه همون jti بدون verifier درست برسه، جواب TOKEN_REPLAYED هست.
  • اگه همون jti با محتوای متفاوت برسه، جواب 409 LAUNCH_PAYLOAD_CHANGED هست.
  • دو ورود هم‌زمان با یک sub توی یک محیط همیشه به یک بازیکن می‌رسن.

۴.۹ ورود دوباره و خطای ورود با postMessage

توی iframe دو صفحه مختلف ممکنه به صفحه شما پیام بدن، هر دو روی Origin بازی. صفحه handoff فان‌لندز (پاسخ launch) فقط funlands:launch_failed رو می‌فرسته. funlands:relaunch_requested رو خود صفحه بازی می‌فرسته، وقتی نشستی نداره: مثلا بعد از reload، یا وقتی refresh با TOKEN_EXPIRED یا SESSION_REVOKED رد شده. توی پیام‌ها هیچ توکن یا subی نمیاد.

{ "type": "partner:relaunch_ready", "request_id": "r_123" }

// از صفحه handoff، اگه ورود یا bootstrap رد بشه
{ "type": "funlands:launch_failed", "code": "TOKEN_EXPIRED", "request_id": "req_01J..." }
  • پیام رو فقط با targetOrigin برابر Origin بازی (FUNLANDS_GAME_ORIGIN) همون محیط بفرستید. موقع دریافت، event.origin رو با همین مقدار و event.source رو با پنجره iframe بسنجید، و برای partner:relaunch_ready همون request_id پیام درخواست رو برگردونید.
  • request_id توی funlands:launch_failed شناسه درخواست launch در فان‌لندزه (همون X-Correlation-Id)، نه شناسه درخواست relaunch. اون رو لاگ کنید و موقع تماس با ما بفرستید. اگه launch از Originی بیاد که ثبت نشده، صفحه handoff ساخته نمیشه، پیامی هم نمیاد و iframe فقط بدنه خطای JSON رو نشون میده.
  • بعد از partner:relaunch_ready، فرم ورود رو با توکن و verifier تازه دوباره داخل iframe بفرستید.
  • اگه سرور شما در دسترس نیست، یک پیام قابل فهم با دکمه تلاش دوباره نشون بدید.

۵. اپ‌های بومی (Android، iOS و TV)

مسیر ورود اپ بومی هنوز نهایی نشده و فعلا فقط ورود وب رو باز می‌کنیم. WebView معمولا Origin قابل اعتماد نمی‌فرسته، پس نمیشه فقط چک Origin رو برداشت و به‌جاش محدودیت نرخ گذاشت. تا وقتی مسیر زیر تصویب و پیاده‌سازی نشده، هیچ مسیر بدون Origin باز نمی‌کنیم. چیزهایی که این مسیر لازم داره:

  • سرور شما ورود رو به‌صورت سرور به سرور برای ما می‌فرسته، با احراز هویت کلاینت یا امضای جدا و یک nonce.
  • ما یک کد handoff کوتاه‌عمر برمی‌گردونیم که به همون دستگاه یا نمونه WebView و به nonce گره خورده.
  • اپ فقط همون کد رو توی WebView باز می‌کنه و ما یک بار مصرفش می‌کنیم. توکن کاربر شما نباید به اپ برسه که باهاش APIهای مختلف رو صدا بزنه.
  • روش اثبات اپ، روش گره زدن به دستگاه و رفتار در قطع شبکه برای Android، iOS و TV هر کدوم جدا بررسی و تایید میشن. User-Agent، IP یا نبودن Origin اثبات حساب نمیشن.

اگه اپ بومی دارید، فهرست اپ‌ها و نسخه‌ها رو توی برگ شریک بنویسید تا این بخش رو با شما نهایی کنیم.

۶. خروج و حذف حساب

۶.۱ خروج از سمت شریک

وقتی کاربر از سرویس شما خارج میشه یا نشستش رو باطل می‌کنید، سرور شما یک توکن خروج امضاشده می‌فرسته:

  • exp اجباریه و exp - iat حداکثر ۱۲۰ ثانیه‌ست. nonce نباید باشه.
  • sid اجباریه. خروج همه نشست‌های یک sub بدون sid فقط با توافق جدا فعال میشه.

اثر خروج فوریه: نشست و کل خانواده refresh باطل میشن، اتصال‌های WebSocket بسته میشن و APIهای حساس وضعیت نشست رو در هر درخواست چک می‌کنن. پس لازم نیست منتظر تموم شدن access token پونزده‌دقیقه‌ای بمونید. بعد از پاسخ 200، صفحه بازی روی access token و refresh همون نشست 401 TOKEN_EXPIRED می‌گیره، چون نشست حذف شده (بخش ۴.۷).

۶.۲ حذف حساب

حذف حساب دو وضعیت جدا داره: «درخواست دریافت شد» و «حذف کامل شد». این دو رو یکی حساب نکنید.

  1. شما درخواست حذف رو با یک request_id پایدار، sub و زمان درخواست می‌فرستید. ارسال دوباره همون request_id اثر دوم نداره.
  2. ما درخواست رو ماندگار ثبت می‌کنیم، همه نشست‌های اون بازیکن رو می‌بندیم و پردازش رو شروع می‌کنیم. جواب در این مرحله فقط یعنی «دریافت شد».
  3. ارتباط هویت و داده شخصی طبق قرارداد داده حذف یا ناشناس میشه. فقط یک رکورد حداقلی برای جلوگیری از تکرار و تایید نگه می‌داریم. آمارهای تجمیعی که واقعا شخصی نیستن طبق توافق می‌مونن.
  4. فقط بعد از کامل شدن حذف، رویداد player.deleted رو براتون می‌فرستیم. این رویداد مدرک کامل شدنه.

نشانی دقیق این درخواست و مهلت کامل شدن حذف هنوز نهایی نیست (بخش ۱۲). تا اون موقع اگه کاربری حسابش رو حذف کرد، دست‌کم توکن خروج رو بفرستید تا نشست‌هاش بسته بشن. player.deleted همین الان هم فرستاده میشه، هر وقت حذف حساب یکی از بازیکن‌های شما در فان‌لندز کامل بشه. چون این حذف از درخواست شما نیومده، request_id این رویداد فعلا همیشه null هست.

۷. رویدادها و وب‌هوک

۷.۱ فهرست رویدادها

هر رویداد این فیلدها رو داره: event_id ثابت، schema_version، subject، player_seq که برای هر بازیکن یکی‌یکی زیاد میشه، و occurred_at به وقت UTC با دقت ثانیه. نوع هر رویداد یک URI هست که از یک پیشوند ثابت و نام کوتاه رویداد ساخته میشه، مثلا https://api.funlands.example/events/game.completed. این پیشوند توی sandbox و production یکسانه و از نشانی پایه API یا issuer محیط ساخته نمیشه. مقدار دقیقش توی برگ شریک میاد و URI رو حرف‌به‌حرف مقایسه کنید. فهرست دقیق فیلدهای هر نوع توی schema نسخه ۱ میاد.

۷.۳ چک کردن امضا در سمت شریک

  1. بدنه با نوع application/secevent+jwt رو به‌صورت متن و با سقف حجم بخونید.
  2. typ باید secevent+jwt باشه، الگوریتم فقط ES256 و kid غیرخالی. توکنی که jku، x5u، jwk، x5c یا crit داره رو رد کنید. SETهای ما هیچ‌وقت این هدرها رو ندارن. denylist خودتون رو هم چک کنید.
  3. کلید رو فقط از نشانی JWKS فان‌لندز که توی برگ شریک گرفتید بخونید.
  4. امضا، iss (issuer فان‌لندز همین محیط) و aud (issuer خود شما) رو با مقدارهای برگ شریک بسنجید، نه با چیزی که داخل درخواست اومده. iat حداکثر ۵ دقیقه قدیمی و حداکثر ۳۰ ثانیه آینده باشه.
  5. تکراری بودن رو با event_id بسنجید، نه با jti. رویداد تکراری هم باید جواب موفق بگیره.
  6. رویداد و رکورد پردازشش رو توی یک تراکنش ماندگار ذخیره کنید و بعد 202 برگردونید. پردازش رو بذارید برای بعد. جواب باید حداکثر توی ۵ ثانیه برسه.
  7. ترتیب رسیدن تضمینی نیست، حتی برای یک بازیکن. آخرین player_seq هر بازیکن رو نگه دارید و اگه فاصله دیدید، علامتش بزنید و از feed بازیابی پرش کنید.
const { payload } = await jwtVerify(body, funlandsJwks, {
  algorithms: ['ES256'], typ: 'secevent+jwt',
  issuer: FUNLANDS_SET_ISSUER, audience: OUR_AUDIENCE,
  requiredClaims: ['iss', 'aud', 'iat', 'jti', 'events'],
  clockTolerance: 30,

۷.۵ تلاش دوباره و dead letter

  • فاصله تلاش‌ها بعد از تلاش اول: ۱ دقیقه، ۵ دقیقه، ۳۰ دقیقه، ۲ ساعت، ۶ ساعت و ۲۴ ساعت، هر کدوم با حداکثر ۱۰٪ jitter و دست‌کم به اندازه Retry-After. بعدش هر ۲۴ ساعت یک بار تا ۷۲ ساعت از اولین تلاش؛ آخرین تلاش درست سر ۷۲ ساعته.
  • بعد از هر خطای گذرا، بقیه رویدادهای محیط شما هم حدود یک دقیقه صبر می‌کنن.
  • توقف (401/403) و dead letter برای تیم عملیات ما هشدار می‌سازن و ما با مخاطب عملیات شما تماس می‌گیریم.
  • اگه رویدادی تا ۷۲ ساعت تحویل نشه، به dead letter میره. ارسال دوباره رو تیم ما ثبت و حسابرسی می‌کنه. رویداد همون event_id اصلی رو نگه می‌داره و پنجره ۷۲ ساعته تازه می‌گیره.
  • خرابی گیرنده شما بازی یا شریک دیگه رو متوقف نمی‌کنه.

۱۰.۲ ساخت کلید و انتشار JWKS

این اسکریپت یک جفت کلید ES256 می‌سازه، کلید خصوصی رو به شکل PKCS#8 توی پوشه secret می‌نویسه و بخش عمومی رو چاپ می‌کنه. اگه فایلی با همون kid وجود داشته باشه، کار رو ادامه نمیده. این روش برای sandbox مناسبه. توی production کلید رو داخل KMS یا HSM بسازید و فقط کلید عمومی رو بیرون بیارید.

// scripts/generate-signing-key.ts
// usage: ts-node scripts/generate-signing-key.ts <kid> <secret-dir>
import { writeFile } from 'node:fs/promises';
import { join } from 'node:path';
import { exportJWK, exportPKCS8, generateKeyPair } from 'jose';

async function main(): Promise<void> {
  const [kid, secretDir] = process.argv.slice(2);
  if (!kid || !secretDir) throw new Error('usage: generate-signing-key <kid> <secret-dir>');

  const { publicKey, privateKey } = await generateKeyPair('ES256', { extractable: true });

  // flag 'wx' refuses to overwrite: a kid is never reused for a new key
  const pem = await exportPKCS8(privateKey);
  await writeFile(join(secretDir, `${kid}.pem`), pem, { mode: 0o600, flag: 'wx' });

  // print only the public part, for review before it goes into the JWKS
  const { kty, crv, x, y } = await exportJWK(publicKey);
  console.log(JSON.stringify({ kty, crv, x, y, kid, alg: 'ES256', use: 'sig' }, null, 2));
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});

سرویس کلید همه فایل‌های پوشه secret رو می‌خونه، چک می‌کنه کلیدها P-256 باشن و فقط بخش عمومی رو منتشر می‌کنه. برای چرخش، فایل K2 رو کنار K1 بذارید تا هر دو منتشر بشن. دست‌کم ۲۴ ساعت بعد PARTNER_ACTIVE_KID رو به K2 عوض کنید و فایل K1 رو دست‌کم ۲۴ ساعت بعد از آخرین امضا بردارید (بخش ۳.۴).

// src/funlands/signing-key.service.ts
import { Inject, Injectable, OnModuleInit } from '@nestjs/common';
import { createPrivateKey, createPublicKey, KeyObject } from 'node:crypto';
import { readdir, readFile } from 'node:fs/promises';
import { basename, join } from 'node:path';
import { funlandsConfig, FunlandsConfig } from './funlands.config';

export interface PublicJwk {
  kty: string; crv: string; x: string; y: string;
  kid: string; alg: 'ES256'; use: 'sig';
}

@Injectable()
export class SigningKeyService implements OnModuleInit {
  private readonly privateKeys = new Map<string, KeyObject>();
  private publicKeys: PublicJwk[] = [];

  constructor(@Inject(funlandsConfig.KEY) private readonly cfg: FunlandsConfig) {}

  async onModuleInit(): Promise<void> {
    const files = (await readdir(this.cfg.signingKeyDir)).filter((f) => f.endsWith('.pem'));
    for (const file of files) {
      const kid = basename(file, '.pem');
      const key = createPrivateKey(await readFile(join(this.cfg.signingKeyDir, file), 'utf8'));
      const curve = key.asymmetricKeyDetails?.namedCurve;
      if (key.asymmetricKeyType !== 'ec' || curve !== 'prime256v1') {
        throw new Error(`Signing key ${kid} is not EC P-256`);
      }
      this.privateKeys.set(kid, key);
    }
    if (!this.privateKeys.has(this.cfg.activeKid)) {
      throw new Error(`No key file for active kid ${this.cfg.activeKid}`);
    }
    // every key in the directory is published: old and new overlap during rotation
    this.publicKeys = [...this.privateKeys].map(([kid, key]) => {
      const jwk = createPublicKey(key).export({ format: 'jwk' });
      return { kty: jwk.kty!, crv: jwk.crv!, x: jwk.x!, y: jwk.y!,
               kid, alg: 'ES256', use: 'sig' };
    });
  }

  /** The key every outgoing token is signed with. */
  active(): { kid: string; key: KeyObject } {
    return { kid: this.cfg.activeKid, key: this.privateKeys.get(this.cfg.activeKid)! };
  }

  /** Public fields only. d never leaves this service. */
  jwks(): { keys: PublicJwk[] } {
    return { keys: this.publicKeys };
  }
}

      ...(user.locale ? { locale: user.locale } : {}),

      ...(user.nickname ? { nickname: user.nickname } : {}),
    })
      .setProtectedHeader({ alg: 'ES256', typ: 'funlands-launch+jwt', kid })
      .setIssuer(this.cfg.issuer)
      .setAudience(this.cfg.launchAudience)
      .setSubject(user.pairwiseSub)
      .setIssuedAt(now)
      .setExpirationTime(now + 120)
      .setJti(randomUUID())
      .sign(key);

    return { launchToken, bootstrapVerifier, game };
  }
}

بعد امضا، typ، iss، aud و سن iat چک میشن. خطای امضا و claim جواب 401 می‌گیره و ما ارسال رو نگه می‌داریم. timeout خوندن JWKS جواب 503 می‌گیره تا دوباره تلاش کنیم. رویدادی که شکلش درست نیست 400 می‌گیره.

  async verify(token: string): Promise<FunlandsEvent[]> {
    let header: ProtectedHeaderParameters;
    try {
      header = decodeProtectedHeader(token);
    } catch {
      throw new UnauthorizedException();
    }
    const forbidden = FORBIDDEN_HEADERS.some((h) => h in header);
    if (forbidden || !header.kid || this.denylist.has(header.kid)) {
      throw new UnauthorizedException();
    }

    let payload: JWTPayload;
    try {
      ({ payload } = await jwtVerify(token, this.jwks, {
        algorithms: ['ES256'],
        typ: 'secevent+jwt',
        issuer: this.cfg.setIssuer,
        audience: this.cfg.setAudience,
        requiredClaims: ['iat', 'jti', 'events'],
        maxTokenAge: '5m',  // iat at most 5 min old
        clockTolerance: 30, // and at most 30 s in the future
      }));
    } catch (err) {
      // JWKS timeout: 503 so Funlands retries. Bad signature or claims: 401.
      if (err instanceof errors.JWKSTimeout) throw new ServiceUnavailableException();
      if (err instanceof errors.JOSEError) throw new UnauthorizedException();
      throw err;
    }

    const events = payload.events;
    if (!events || typeof events !== 'object' || Object.keys(events).length === 0) {
      throw new BadRequestException();
    }
    const entries = Object.entries(events as Record<string, Partial<FunlandsEvent>>);
    return entries.map(([type, body]) => {
      if (typeof body?.event_id !== 'string' || typeof body.player_seq !== 'number') {
        throw new BadRequestException();
      }
      return { ...body, type } as FunlandsEvent;
    });
  }
}

  abstract saveAll(events: FunlandsEvent[]): Promise<void>;
}

    super();
  }

  async saveAll(events: FunlandsEvent[]): Promise<void> {
    const client = await this.pool.connect();
    try {
      await client.query('BEGIN');
      for (const e of events) {
        await client.query(
          `INSERT INTO funlands_event_inbox
             (event_id, event_type, player_sub, player_seq, occurred_at, payload)
           VALUES ($1, $2, $3, $4, $5, $6)
           ON CONFLICT (event_id) DO NOTHING`,
          [e.event_id, e.type, e.subject.sub, e.player_seq, e.occurred_at, JSON.stringify(e)],
        );
      }
      await client.query('COMMIT');
    } catch (err) {
      await client.query('ROLLBACK');
      throw err;
    } finally {
      client.release();
    }
  }
}

// src/funlands/funlands-api.error.ts
export class FunlandsApiError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,
    readonly correlationId?: string,
    readonly retryAfterSeconds?: number,
  ) {
    super(`Funlands ${status} ${code} correlation_id=${correlationId ?? '-'}`);
  }

  static async from(res: Response): Promise<FunlandsApiError> {
    const body = (await res.json().catch(() => ({}))) as {
      code?: string; error?: string; retry_after_seconds?: number;
    };
    const retryAfter = Number(res.headers.get('retry-after') ?? body.retry_after_seconds);
    // API errors carry code, /oauth/token errors carry the OAuth error field
    return new FunlandsApiError(res.status, body.code ?? body.error ?? 'UNKNOWN',
      res.headers.get('x-correlation-id') ?? undefined, Number.isFinite(retryAfter) ? retryAfter : undefined);
  }
}

// src/funlands/funlands-logout.service.ts
import { Inject, Injectable, Logger } from '@nestjs/common';
import { randomUUID } from 'node:crypto';
import { setTimeout as sleep } from 'node:timers/promises';
import { SignJWT } from 'jose';
import { FunlandsApiError } from './funlands-api.error';
import { funlandsConfig, FunlandsConfig } from './funlands.config';
import { SigningKeyService } from './signing-key.service';

const LOGOUT_EVENT = 'http://schemas.openid.net/event/backchannel-logout';

@Injectable()
export class FunlandsLogoutService {
  private readonly logger = new Logger(FunlandsLogoutService.name);

  constructor(
    @Inject(funlandsConfig.KEY) private readonly cfg: FunlandsConfig,
    private readonly keys: SigningKeyService,
  ) {}

  /** Call when the user signs out or we revoke the session sent as sid. */
  async logout(pairwiseSub: string, sessionId: string): Promise<void> {
    const { kid, key } = this.keys.active();
    const now = Math.floor(Date.now() / 1000);
    const logoutToken = await new SignJWT({ sid: sessionId, events: { [LOGOUT_EVENT]: {} } })
      .setProtectedHeader({ alg: 'ES256', typ: 'logout+jwt', kid })
      .setIssuer(this.cfg.issuer)
      .setAudience(this.cfg.logoutAudience)
      .setSubject(pairwiseSub)
      .setIssuedAt(now)
      .setExpirationTime(now + 120) // no nonce claim
      .setJti(randomUUID())
      .sign(key);

    const url = new URL('/partner/v1/backchannel-logout', this.cfg.funlandsBaseUrl);
    for (let attempt = 1; attempt <= 3; attempt++) {
      try {
        const res = await fetch(url, {
          method: 'POST',
          headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
          body: new URLSearchParams({ logout_token: logoutToken }),
          signal: AbortSignal.timeout(5_000),
        });
        if (res.ok) return; // 200: done now or already done before
        const error = await FunlandsApiError.from(res);
        // other 4xx is a configuration problem: do not retry
        if (res.status < 500 && res.status !== 429) throw error;
        this.logger.warn(`logout attempt ${attempt} failed: ${error.message}`);
      } catch (err) {
        if (err instanceof FunlandsApiError) throw err;
        this.logger.warn(`logout attempt ${attempt} failed: network`); // never log the token
      }
      if (attempt < 3) await sleep(attempt * 2_000);
    }
    throw new Error('Funlands logout not confirmed: queue it and retry later with a fresh token');
  }
}

۱۱. چک‌لیست قبل از production

همه این موارد باید روی sandbox واقعی، نه روی نمونه‌های این سند، پاس بشن و نتیجه‌شون ثبت بشه.

کلید

  • JWKS فقط کلید عمومی داره، هر کلید kid و alg داره و نشانیش بدون ریدایرکت جواب میده.
  • چرخش کامل تمرین شده: انتشار K2، امضا با K2، قبول K1 و K2 در هم‌پوشانی، و حذف K1.
  • ابطال اضطراری تمرین شده: بعد از اعلام، توکن K1 با exp معتبر رد میشه.
  • توکن با kid ناشناخته، alg=none، HS256 یا هدر jku رد میشه.
  • کلید و توکن sandbox روی production قبول نمیشه، و اگه دو شریک kid یکسان داشته باشن، توکن یکی به اسم اون یکی قبول نمیشه.

ورود و نشست

  • ورود معتبر، و ورود دوباره با همون sub که به همون بازیکن می‌رسه.
  • همون sub توی production بعد از بازی در sandbox یک بازیکن جدا می‌سازه و گزارش هر محیط فقط بازیکن همون محیط رو نشون میده.
  • دو ورود هم‌زمان یک بازیکن می‌سازن.
  • توکن منقضی، عمر بیشتر از ۱۲۰ ثانیه، iat آینده، aud اشتباه و نبود typ رد میشن.
  • اگه Origin نباشه یا ثبت‌نشده باشه، درخواست رد میشه.
  • فرم launch، frame-src، form-action و چک postMessage همه با Origin بازی (FUNLANDS_GAME_ORIGIN) همون محیط تنظیم شدن، نه با نشانی پایه API.
  • صفحه بازی بعد از bootstrap فقط Authorization: Bearer (و توی WebSocket فقط auth.token) می‌فرسته، هیچ کلید یا سکرت شریکی توی صفحه بازی یا مرورگر نیست، و درخواستی که توکن داره با کلید شریک دیگه 403 PARTNER_TOKEN_MISMATCH می‌گیره.
  • verifier اشتباه رد میشه، و تکرار ورود بعد از مصرف کد طبق بخش ۴.۸ رفتار می‌کنه.
  • هیچ توکن، کد یا verifierی توی URL یا لاگ‌های شما نیست.
  • relaunch بعد از reload و بعد از قطع موقت سرور شما کار می‌کنه.
  • کاربر با رده سنی ناشناخته محتوای محدودشده نمی‌بینه.

خروج

  • بعد از توکن خروج، نشست و WebSocket فورا بسته میشن و refresh با 401 TOKEN_EXPIRED (یا اگه زودتر از حذف نشست برسه، SESSION_REVOKED) رد میشه و صفحه بازی ورود تازه می‌خواد.
  • صفحه بازی بعد از غیرفعال شدن شریک با TOKEN_EXPIRED یا SESSION_REVOKED درست رفتار می‌کنه و توی حلقه refresh نمی‌افته.
  • توکن خروج تکراری 200 می‌گیره و توکن خروج بدون exp رد میشه.

رویداد

  • گیرنده شما امضا، iss، aud و سن iat رو چک می‌کنه و تکرار رو با event_id تشخیص میده.
  • 202 فقط بعد از ذخیره ماندگار برمی‌گرده.
  • ارسال تکراری با SET تازه و همون event_id فقط یک بار پردازش میشه.
  • رفتار درست در 429 با Retry-After، 5xx، timeout، dead letter و replay.
  • رویداد خارج از ترتیب و فاصله در player_seq با feed بازیابی پر میشه.

گزارش و داده

  • API گزارش توکن بازی رو رد می‌کنه و assertion تکراری هم رد میشه.
  • با external_sub شریک دیگه هیچ داده‌ای برنمی‌گرده.
  • عددهای پنل و API برای یک بازه یکی هستن.
  • پیام‌های فارسی خطا به‌صورت دستی در حالت RTL مرور شدن.

عملیات

  • کانال حادثه دوطرفه، مخاطب عملیات و مخاطب امنیت ثبت و یک بار امتحان شدن.
  • عددهای کش، اختلاف ساعت و مهلت اعلام حادثه توی برگ عملیاتی دو طرف نوشته شدن.

۱۲. موارد باز

این‌ها هنوز نهایی نیستن. تا وقتی نهایی نشدن، هیچ‌کدوم از شکل‌های پیشنهادی‌شون رو پیاده‌سازی نکنید.

موضوعوضعیت
API رویدادهای فنی بازیپنل پوسته‌ها به رویدادهایی مثل Load، Run، Start، پایان مرحله و Crash نیاز داره، ولی API دریافتش هنوز تعریف نشده. یک طرح پیشنهادی داریم که تایید نشده. این عددها فقط telemetry هستن و مبنای امتیاز یا شاخص رسمی نمیشن.
ورود اپ بومیمسیر handoff سرور به سرور، شکل درخواست و روش گره زدن به دستگاه برای Android، iOS و TV هنوز تعریف نشده (بخش ۵).
حذف حسابنشانی درخواست، شکل پیام (مثلا یک SET امضاشده)، مسیر پیگیری وضعیت و مهلت کامل شدن حذف تا امضای سیاست داده باز می‌مونن.
پروفایل خروجالان typ: logout+jwt رو قبول می‌کنیم. پذیرفتن مقدار دیگه، استفاده از پروفایل کامل OIDC Back-Channel Logout و خروج بدون sid هنوز توافق نشده.
عددهای هر شریکمجموعه مقدارهای age_band، محدودیت‌های نرخ، مدت نگهداری داده، مسیر ماندگاری و خروجی فایل توی برگ هر شریک نهایی میشن.
